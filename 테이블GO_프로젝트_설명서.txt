(비개발자를 위한 쉬운 설명)
작성일: 2026-08-12
최종 업데이트: 2026-08-13


===================================
1. 테이블GO가 뭔가요?
===================================

테이블GO는 식당 테이블을 예약할 수 있는 작은 웹 서비스입니다.
크게 두 개의 화면(웹사이트)으로 이루어져 있습니다.

  1) 손님용 예약 사이트
     주소: https://table-go-nine.vercel.app
     - 누구나 로그인 없이 들어와서 날짜와 시간을 골라 예약할 수 있습니다.
     - 영업시간은 10:00~22:00, 2시간 단위로 하루에 6개 시간대가 있습니다.
     - 한 시간대에 최대 3팀까지 함께 예약할 수 있습니다.
     - 토요일, 일요일은 자동으로 휴무 처리됩니다.

  2) 사장님(직원)용 관리자 페이지
     주소: https://table-go-admin.vercel.app
     - 로그인을 해야 들어갈 수 있는 내부 관리 화면입니다.
     - 오늘/전체 예약 현황을 확인하고, 예약을 취소할 수 있습니다.
     - 예약 통계, 손님 만족도 설문 결과도 여기서 볼 수 있습니다.

두 사이트는 화면 오른쪽 위/아래에 있는 "관리자 로그인", "예약 사이트 보기"
버튼으로 서로 연결되어 있어서, 손님용 사이트에서 관리자 사이트로,
관리자 사이트에서 손님용 사이트로 바로 이동할 수 있습니다.


===================================
2. 2026-08-12에 새로 만든 / 고친 기능
===================================

(1) 실시간 예약 현황 업데이트
    - 예전에는 예약 페이지를 새로고침해야 다른 사람이 방금 예약했는지
      알 수 있었습니다.
    - 이제는 새로고침 없이도 자동으로 확인해서, 다른 손님이 그 시간대를
      예약하면 버튼이 즉시 "마감"으로 바뀌고, 예약이 취소되면 다시
      "예약 가능"으로 바뀝니다.
    - 달력에서도 하루 시간대가 전부 찼으면 "마감" 표시가 뜹니다.

(2) 중복 예약 방지
    - 두 사람이 동시에 같은 시간대를 예약 버튼을 누르는 극단적인 상황을
      대비해서, 서버(데이터를 저장하는 컴퓨터)에서 저장하기 직전에
      "이 시간, 진짜 아직 비어있나?"를 한 번 더 확인합니다.
    - 그래도 정말 딱 동시에 눌렀을 경우를 대비해서, 데이터베이스
      (예약 정보가 저장되는 곳) 자체에도 규칙을 걸어놨습니다. 이 규칙
      덕분에 어떤 경우에도 정원을 넘는 이중 예약이 물리적으로
      불가능합니다.
    - 만약 두 사람이 거의 동시에 눌렀다면, 늦게 누른 사람에게는
      "죄송합니다. 해당 시간은 방금 예약되었습니다. 다른 시간대를
      선택해주세요." 라는 안내 메시지가 뜹니다.

(3) 손님용 사이트 ↔ 관리자 사이트 연결
    - "관리자 로그인" / "예약 사이트 보기" 버튼으로 두 사이트를
      서로 연결했습니다.

(4) 인터넷에 실제로 배포 (포트폴리오용)
    - GitHub(코드 저장소)에 코드를 올리고, Vercel로 실제 인터넷
      서비스로 켰습니다.
    - 저장 위치: https://github.com/djdw2657/table-go

3. 2026-08-13에 새로 만든 기능
===================================

(1) 예약 확정 이메일 자동 발송
    - 예약이 완료되면 손님에게는 "예약 확정" 메일이, 식당 앞으로는
      "새 예약 1건" 메일이 자동으로 발송됩니다.
    - 손님용 메일에는 예약 정보와 함께 "예약 변경" / "예약 취소"
      버튼이 들어있어서, 클릭하면 바로 확인 화면으로 이동합니다.
    - Resend라는 이메일 발송 서비스를 사용했고, 발송 키는 코드에
      직접 적지 않고 안전한 별도 저장소(환경변수)에 보관했습니다.

(2) 대기자 등록 기능
    - 원하는 시간대가 마감됐으면 "대기 등록" 버튼으로 이름·연락처·
      이메일을 남길 수 있습니다.
    - 누군가 취소하면 대기 1번에게 자동으로 "자리가 났습니다" 메일이
      발송되고, 메일의 링크로 들어가면 바로 예약을 확정할 수 있습니다.
    - 24시간 안에 확정하지 않으면 자동으로 다음 대기자에게 순서가
      넘어갑니다.
    - 관리자 페이지 달력에서 시간대별 대기 인원도 확인할 수 있습니다.

(3) 데이터베이스를 Supabase로 이전 (실시간 기능 강화)
    - 기존에 쓰던 데이터베이스 서비스(Neon)에서, 실시간 기능을 더
      잘 지원하는 Supabase라는 서비스로 옮겼습니다.
    - 기존에 저장돼 있던 예약·휴무일 정보는 하나도 빠짐없이 그대로
      옮겨졌습니다 (이전 후 개수를 대조해서 확인했습니다).
    - "예약이 찼다/취소됐다" 같은 변화가 생기면, 개인정보는 전혀
      담기지 않은 "뭔가 바뀌었다"는 신호만 실시간으로 화면에
      전달되고, 화면은 그 신호를 받으면 다시 최신 정보를 안전하게
      조회해옵니다. (손님 이름·연락처 같은 정보가 실시간 통신
      과정에서 새어나갈 수 있는 방식은 처음부터 배제했습니다.)

(4) 식사 후 만족도 설문 자동 발송
    - 예약 시간이 지나면 예약이 자동으로 "이용완료" 상태로 바뀌고,
      그로부터 24시간 뒤 손님에게 만족도 설문 메일이 자동으로
      발송됩니다.
    - 설문 문항: 음식 별점(1~5), 서비스 별점(1~5), 추천 의향(0~10),
      자유 코멘트.
    - 설문 메일을 보내고 3일이 지나도 응답이 없으면, 리마인더 메일을
      한 번 더 보냅니다.
    - 관리자 페이지에서 평균 별점, 평균 추천 점수, 최근 코멘트,
      일자별 응답률을 그래프로 볼 수 있습니다.
    - 이 자동 발송은 Supabase의 "Edge Function"이라는 기능이 매시간
      정각에 스스로 확인하고 실행하는 방식으로 동작합니다 (사람이
      매번 눌러줄 필요가 없습니다).

4. 어떤 기술로 만들었나요? (쉬운 비유로)
===================================

- Next.js (넥스트.js)
  화면(버튼, 글자, 달력 등)을 그리고 사용자 요청을 처리하는 핵심
  뼈대입니다. 레스토랑으로 치면 '주방+홀 운영 시스템' 같은 것입니다.

- 데이터베이스 (Supabase / Postgres)
  예약 정보, 시간대 정보, 대기자 명단, 설문 응답이 실제로 저장되는
  곳입니다. 손님 정보와 예약 내역이 적힌 '장부'라고 보시면 됩니다.
  2026-08-13에 Neon에서 Supabase로 옮기면서, 이 장부의 변화를
  실시간으로 화면에 알려주는 기능(Realtime)도 함께 얻었습니다.

- Prisma (프리즈마)
  프로그램이 저 '장부'(데이터베이스)를 안전하고 정확하게 읽고
  쓰도록 도와주는 도구입니다.

- Clerk (클럭)
  관리자 페이지의 로그인 기능을 담당합니다. 아이디/비밀번호를
  직접 관리하는 대신 검증된 외부 서비스를 빌려 쓰는 방식입니다.

- Resend (리센드)
  예약 확정, 대기자 알림, 만족도 설문 등 모든 자동 이메일 발송을
  담당하는 서비스입니다.

- 모노레포 (Monorepo)
  이 프로젝트 하나 안에 손님용 사이트, 관리자 사이트, 그리고 뒤에서
  자동 작업(크론)을 처리하는 사이트까지 여러 개의 작은 프로그램이
  함께 들어있는 구조입니다. 공통으로 쓰는 부품(디자인, 데이터베이스
  연결 등)을 한 곳에 모아 같이 관리해서 효율적입니다. next-forge라는
  이름의 완성된 뼈대(템플릿)를 기반으로 시작했습니다.

- GitHub / Vercel / Supabase
  GitHub는 코드 보관, Vercel은 손님용·관리자용·자동작업용 세 사이트를
  실제 서비스로 켜는 역할, Supabase는 데이터베이스와 자동 이메일
  발송(설문) 역할을 담당합니다.

5. 배포하면서 실제로 겪은 문제와 해결 (참고용)
===================================

인터넷에 실제로 서비스를 켜는 과정에서, 내 컴퓨터에서는 멀쩡히
되던 것이 실제 서버에서는 안 되는 경우가 몇 번 있었습니다.
개발에서 흔히 있는 일이며, 하나씩 원인을 찾아 고쳤습니다.

  [2026-08-12]
  - 블로그/약관 페이지가 예약 기능과 무관한 외부 콘텐츠 서비스
    (BaseHub)에 연결되어 있었는데, 그 서비스 계정을 만들지 않아서
    배포가 막혔습니다. → 예약 기능에 필요 없는 페이지라 삭제했습니다.
  - 관리자 페이지 로그인 화면 관련 코드에 오래된 버그가 있어서
    실제 배포 시 빌드가 실패했습니다. → 코드를 수정해서 해결했습니다.
  - 예약 페이지가 실제 서버에서 데이터베이스에 접속할 때 사용하던
    연결 방식(웹소켓)이 불안정해서 오류가 났습니다. → 더 안정적인
    연결 방식(HTTP)으로 바꿔서 해결했습니다.
  - 두 개의 사이트(손님용/관리자용)가 서로의 정확한 인터넷 주소를
    몰라서 "관리자 로그인", "예약 사이트 보기" 링크가 깨져있었는데,
    실제 배포된 주소로 값을 넣어줘서 해결했습니다.

  [2026-08-13]
  - 데이터베이스를 Supabase로 옮기는 과정에서, 자동 이메일 발송
    기능(설문)이 "권한 없음" 오류로 조용히 실패하고 있었습니다.
    → 자동 발송 기능이 데이터베이스를 들여다볼 수 있는 권한을
    깜빡하고 안 열어줬던 것을 찾아서 권한을 추가했습니다.
  - 뒤에서 자동 작업(대기자 정리, 예약 자동완료)을 처리하는 새
    사이트를 추가로 배포했는데, 처음엔 설정이 꼬여서 관련 없는
    다른 부품들까지 전부 다시 만들려다가 빌드가 실패했습니다.
    → 이 사이트가 정확히 어느 폴더의 코드로 만들어져야 하는지
    설정을 바로잡아서 해결했습니다.
  - 대기자/설문 링크 페이지가 실제로는 데이터가 있는데도 "페이지를
    찾을 수 없음"으로 뜨는 문제가 있었습니다. → 이런 링크는 매번
    최신 정보를 다시 확인해야 하는데, 서버가 예전 응답을 "저장해
    두고 재사용"해버려서 생긴 문제였습니다. 항상 새로 확인하도록
    설정을 고쳤습니다.

6. 앞으로 더 추가하면 좋을 기능 (아이디어)
